## 跨仓库规律总结

### 规律一：`allowed-tools` 遗漏是本周最常见的失分点

11 个仓库中，**7 个**存在 `allowed-tools` 缺失问题，覆盖从 63 分到 99 分的全分值段：

| 仓库 | 分数 | 涉及文件数 |
|---|---|---|
| FlorianBruniaux/claude-code-ultimate-guide | 80 | 5 个 skill |
| Dammyjay93/interface-design | 94 | 5 个 command |
| BayramAnnakov/claude-reflect | 99 | 1 个（view-queue.md 多余声明） |
| AgriciDaniel/claude-ads | 99 | 2 个 command |
| AgriciDaniel/claude-blog | 92 | 3 个 command |
| 0xfurai/claude-code-subagents | 74 | 多处 |
| 777genius/claude-notifications-go | 63 | 多处 |

**根本原因**：`allowed-tools` 属于「隐式知识」——新手作者不知道需要声明，老手作者觉得「不声明也能跑」就懒得加。NLPM 规则将它列为 -5 分项，但实际上不影响功能，所以优先级排在最后。

**学习结论**：这不是作者能力问题，而是 Claude Code 文档未将 `allowed-tools` 在「入门教程」中突出。我需要在自己的模板中把 `allowed-tools` 列为 frontmatter 必填项，而非可选项。

### 规律二：注册机制缺失（missing `name:`）与内容质量完全无关

本周最极端的对比：
- **LigphiDonk/Oh-my--paper**（65/100）：拥有 35 个精心设计的研究 skill（avg 77/100），但 10 个 agent 和 16 个 command 全部缺 `name:` frontmatter，导致整个插件不可安装使用
- **AgriciDaniel/claude-ads**（99/100）：内容精简但注册字段完整

「内容丰富但无法安装」比「内容简单但可以安装」更让用户沮丧。**注册机制是插件可用性的地基**，其他所有功能都建立在它之上。

**学习结论**：每次新建 agent/command 文件，先写 frontmatter 的三个必填字段（`name`、`description`、`model`/类型），再写内容。顺序不能颠倒。

---

### 规律三：安全问题集中在「执行流量控制」和「外部依赖引入」两类

本周出现 3 种安全模式：

**A. curl-pipe-外部 shell**（FlorianBruniaux，CRITICAL）
```bash
# diagnose.md 第39行 —— 极高风险
curl -sL "https://raw.githubusercontent.com/flobby41/...audit-scan.sh" | bash -s -- --json
```
特殊风险：`flobby41` 不是仓库作者账号，是第三方（或作者旧账号），用户运行时实际信任了一个不可控的代码源。

**B. `--dangerously-skip-permissions` 写入 skill 默认值**（LigphiDonk）
权限绕过指令写进 skill 意味着所有读取该 skill 的 agent 都默认运行在最高权限模式，形成「权限扩散」。

**C. 隐性外部依赖**（LigphiDonk，`/codex:rescue`）
命令体中到处引用 `/codex:rescue` 但从未声明依赖，用户安装后调用任何命令都会遭遇「未知命令」错误。

**学习结论**：3 类安全模式的共同特征是「隐式信任」——信任第三方脚本、信任权限绕过是无害的、信任用户已安装依赖。我的插件里不应出现任何隐式信任。

### 规律四：高分仓库的共同特征是「意图先于代码」

本周 90+ 分仓库（AgriciDaniel 系列 91-99、BayramAnnakov 99、Dammyjay93 94）共享一个设计哲学：**在 agent/command 生成代码之前，先让用户或 AI 明确意图**。

具体表现：
- **AgriciDaniel/claude-ads（99/100）**：command 开头要求确认广告目标和受众
- **Dammyjay93/interface-design（94/100）**：SKILL.md 的「Intent First」章节强制 AI 在写第一行代码前回答三个设计问题
- **BayramAnnakov/claude-reflect（99/100）**：Stage 1（自动捕获）只收集，Stage 2（人工 `/reflect`）才写入，人始终保持决策权

低分仓库（63-74 分）则倾向于直接执行，缺少「暂停-确认-执行」的节奏。

**学习结论**：「意图门控」是高质量 NL artifact 的标志性结构。任何涉及副作用（写文件、修改配置、发送请求）的 command 都应该在执行前有一个意图确认步骤。

### 规律五：静默失败比显式报错更危险

本周出现两种「静默失败」模式：

1. **BayramAnnakov/claude-reflect**：`$0` 路径解析在 Claude Code 的 `!` 上下文中失败，但 `|| echo "[]"` 将失败伪装成「空队列」，用户永远不会知道脚本没有实际运行
2. **FlorianBruniaux**：`plugin.json` 中缺少 `hooks` 字段可能导致 hook 静默跳过注册，用户只会看到「hook 不工作」但没有错误提示

两个案例都导致高 NL 分数（99/100 和 80/100）与实际运行时功能之间存在差距。**NLPM 静态分析无法检测运行时静默失败**。

**学习结论**：在我的 hook 脚本中，失败路径应该向 stderr 输出明确的错误信息，而不是静默降级。`|| echo "[]"` 是开发时的便利，不是生产配置的选择。

### 规律六：设计文档的维护比代码更难

| 仓库 | 在 audit 后修复的 | 未修复的 |
|---|---|---|
| Dammyjay93/interface-design | references/ 目录（3 个 broken link 全部修复） | allowed-tools（5 个 command 全部未修复） |
| BayramAnnakov/claude-reflect | 无 | plugin.json hooks 字段（7 周未修复） |
| FlorianBruniaux | 无 | curl flobby41（CRITICAL，3 周未修复） |
| LigphiDonk/Oh-my--paper | 无 | 10 个 agent 无 frontmatter（3+ 周未修复） |

修复模式：**影响功能的 bug 先修**（Dammyjay 的 broken link 影响用户访问深度参考）；**不影响基本功能的质量问题**（allowed-tools、vague quantifier）基本不修。

这解释了一个现象：NLPM 的 -5 分小罚项（允许-tools 缺失）在作者的优先级列表中低于「用户能不能用」。

**学习结论**：NLPM 质量问题的修复优先级应该是：阻断性 bug > 安全问题 > 可见功能影响 > 质量规范。我自己做 code review 时也应该用同样的优先级排序。

## 本周学到的最有价值的 3 个模式

### #1：System.md 模式（来自 Dammyjay93）
在用户项目中维护一个 `system.md` 记录设计签名，实现跨会话一致性。这是一种「外部化工作记忆」的架构：把 AI 在会话中建立的认知锚点持久化为文件，避免下次会话从零重建。

**可立即借鉴的场景**：代码风格维护、架构决策记录、用户偏好追踪。

### #2：双阶段捕获-确认架构（来自 BayramAnnakov）
自动捕获（hook）只做队列化，人工命令（/reflect）才做写入。这个设计把「AI 的判断」和「用户的决策」分在两个时间点，既保持了自动化的便利，又不剥夺用户的掌控感。

**可立即借鉴的场景**：任何需要持久化 AI 推断结果的系统（记忆、偏好、规则）。

### #3：富元数据 Frontmatter（来自 LigphiDonk 的 dr-claw 上游）
在 skill frontmatter 中加入 `stages`、`primaryIntent`、`capabilities`、`upstream.repo/revision` 等字段，使 skill 不仅可以被加载，还可以被分类、版本追踪和溯源。

**可立即借鉴的场景**：当 skill 库超过 10 个时，这些字段的价值开始显现——路由、审计、更新管理都依赖它们。
