数字的解读：「共享基础设施聚合式」的 78 分不是因为每个 skill 写得差——ccplugins 有几个质量极高的插件（commit-commands 98 分、pr-review-toolkit 91-94 分）。问题是**没有 CI 质量门**，导致低质量 PR 通过率高，拉低了整体平均分。

「参考实现锚定式」（6 skills，89/100）和「三层分离」（15 skills，93/100）得到了最干净的分布——高分文件多，低分文件极少。核心原因：**约束创建质量**。symphony 的约束是「对齐 commit/SKILL.md 的五段结构」，n8n-skills 的约束是「所有 skill 必须在 `description` 字段声明触发词集合」。

**行动意义**：
1. 如果要建一个「多 skill 仓库」，必须先定义一个内部质量标准（一个高分参考实现 + 一个 CI 校验脚本）再开始批量创建

### 认知 3：「删除解决」和「修复解决」同样合理，关键是不留含糊状态

本周两个仓库都面对了「硬编码路径导致 skill 对 99% 用户无效」的问题，处理方式不同：

- **agent-sh/agentsys**：直接**删除** `web-auth` 和 `web-browse`（含 40+ 处 `/Users/avifen/` 硬编码路径），不保留任何残骸
- **pbakaus/impeccable**：**修复** `new Function(动态字符串)` → 换成静态 import；**重构** `CLAUDE.md` 中的 stale reference → 改为「见私有仓库路径」

两种做法都比「标记为已知问题但保留」要好得多。agentsys 的「删除」体现了一个判断：维护不可移植的 skill 的长期成本 > 短期重写成本，而且这两个 skill 对原作者之外的所有用户已经是死代码。impeccable 的「修复」体现了另一个判断：`new Function()` 是可以用标准 ESM import 替换的，不需要删除整个构建脚本。

ccplugins 的负面案例做了对比：59 个截断描述、3 个 name mismatch bug，**既没有删除，也没有修复**，只是保留着——3 个月后仍然原样。这种「明知有 bug，悬而不决」的状态比删除或修复的代价都高，因为它会在用户每次安装时触发，而维护者根本不知道。

**行动意义**：处理有缺陷的 skill 只有两种正确答案：（1）修复它到可用状态；（2）删除它。「保留已知有问题的版本」会对用户静默失败，是最差选项。自查：我的项目里有没有「已知有问题但没删也没修」的 skill？
