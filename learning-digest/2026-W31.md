**curl\|bash 出现在 2 个独立仓库的 4 个独立脚本里**——这不是个别情况，而是「快速安装」文化的系统性后果。维护者的心智模型是「这是安装脚本，不是运行时代码」，但安全扫描器无法分辨善意 pipeline。

**关键洞察**：防止 curl\|bash 不需要复杂措施。替代方案是在 README 里列出安装步骤（curl 下载 → 用户审核 → 手动 bash），或使用包管理器（npm / brew / cargo install）。这两种替代方式对维护者的成本几乎为零，但对安全的改善是从 BLOCKED → CLEAR。

**自查**：MarkQWu 的所有仓库里有没有 `install.sh`？如果有，是否用了 `curl | bash`？目标是在任何安装脚本里找到并替换这个模式。

### 认知 3：跨会话持久化的三种成熟方案并排出现——选择取决于环境假设，而非优劣

本周三个仓库各自用不同架构解决了「AI agent 如何在会话结束后记住状态」这个相同问题：

| 方案 | 仓库 | 核心实现 | 环境假设 | 对用户的可见性 |
|---|---|---|---|---|
| **MCP 状态机** | jnuyens/gsd-plugin | `HANDOFF.json` + MCP server，结构化 handoff schema | 用户有持续运行的 MCP 环境 | 不可见（MCP 后台） |
| **可移植二进制文件** | memvid/claude-brain | `.claude/mind.mv2`（Rust SDK 压缩）可 `git commit` | 用户愿意安装原生依赖 | 不可见（二进制） |
| **Markdown 记忆文件** | pe-menezes/fin-claude-plugin | 4 个 `.md` 文件（`Preferências.md` 等），跨 6 个 skills 一致引用 | 零外部依赖，用户能打开 .md 文件 | 完全可见（人类可读） |

三种方案在各自的假设下都是正确的：
- gsd 作者本身就在用 MCP 生态，HANDOFF.json 给他一个结构化的会话恢复协议，下次接着做；
- memvid 用户需要在多台机器、多个项目间共享记忆，git commit 是最自然的分发方式；
- fin 用户需要随时打开文件检查「Claude 记住了我哪些财务偏好」，可读性比可查询性更重要。

**值得注意的第四条路**：uppinote20/claude-dashboard 和 agent-sh/agnix 都用 TypeScript/Rust 原生层处理状态，而 NL 层只读取不写入。这是「NL 表皮 + 二进制核心」模式的持久化变体：NL 不负责状态管理，原生层负责。

**行动意义**：在设计自己的跨会话状态时，首先问：「用户的环境里一定有 MCP 吗？」如果不确定，Markdown 文件是最保险的起点——零依赖，向任何方向迁移的成本最低。
