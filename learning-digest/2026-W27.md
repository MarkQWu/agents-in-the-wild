| nyldn/claude-octopus | 157 | 79/100 |
| rohitg00/awesome-claude-code-toolkit | 558 | **46/100** |

这不是随机噪音。机制是：
1. **命名一致性崩溃**：制品越多，`name` 字段、`allowed-tools` 声明等机械规则越难全面覆盖。nyldn 的 157 个 artifact 里，44/49 个 command 缺 `allowed-tools`（65%）。
2. **交叉引用漂移**：n-skills 的 5 个 skill 之间无引用关系，零断链；octopus 的 157 个制品里出现多处指向不存在文件的引用。
3. **维护注意力稀释**：peterkrueck 的 skill 层（7 个文件，均分 93/100）写得极好；command 层（2 个文件，均缺 frontmatter）明显被忽视了。

结论不是"不要添加制品"，而是**每增加一批制品，都要同步运行一次 `/nlpm:score` 捞出机械性失误**。累积的债务在 100+ 文件后就变成无法一次性清偿的负担。

**行动意义**：drama-workshop-skills 计划新增 skill 之前，先给现有文件跑 `/nlpm:score`，确认零机械债才扩张。

### 认知 3：守护者悖论——安全工具自身成为攻击面

本周出现了一个具有教学意义的讽刺案例：

**peterkrueck/Claude-Code-Development-Kit** 的 `hooks/security-scan.sh` 是一个 PostToolUse 安全扫描器，声称能检测敏感文件写入。但 NLPM 审计发现这个脚本本身有 HIGH 级漏洞：它用字符串插值把 `$file` 拼进 JSON 模板，却没有对文件名做转义。文件名包含空格、引号或 `\n` 时，生成的 JSON 会被破坏，甚至可以注入任意 JSON 字段。

守护者悖论：
- 安全 hook 运行频率最高（每次工具调用都触发）
- 安全 hook 处理的输入最不可信（文件路径来自项目，用户可控）
- 安全 hook 如果被利用来输出虚假结论，能压制真实发现（defender is the attacker's target）

类似模式在 rtk-ai/rtk 里也出现：`scripts/benchmark.sh` 包含 `eval` 来动态构建命令——这在测试脚本里看似"内部可信"，但只要仓库接受外部输入（benchmark 参数、测试配置），eval 就是一个等待被触发的注入点。

两个案例的共同根因：**我们在写安全基础设施时，会降低对它本身的安全审查强度**，因为直觉上觉得"这是我们的防线，不是攻击目标"。

**行动意义**：任何处理外部输入（文件路径、命令行参数、JSON payload）的 hook 或脚本，在 code review 时优先级要**高于**普通业务逻辑，而不是相反。写 hook 时默认对所有字符串变量加引号（`"$var"` 而非 `$var`），对文件路径做 `printf '%q'` 转义。
