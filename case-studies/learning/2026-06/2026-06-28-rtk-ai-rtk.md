## 一、理解（基于 audit 快照）

### 1.1 仓库概览

rtk-ai/rtk 是一个 **Redux Toolkit 命令行代码模板生成器**，在工具核心之上叠加了一套完整的 Claude Code AI 辅助层。项目拥有 28660 颗星，是 CLI 工具与 AI 工作流集成的代表性高星仓库。

从 Audit 快照看，仓库包含 33 个 NL（自然语言编程）制品，覆盖 skill、agent、command、hook 四个层次。NL 质量评分为 88/100，属于工程实践良好但存在机械性问题的典型案例。安全评级为 **BLOCKED**（含 3 项 Critical 安全发现），在贡献流水线中被自动阻断。

项目的核心价值主张有两层：其一是面向 React/Redux 开发者的脚手架 CLI，提供一致的代码模板；其二是将这套 CLI 工具封装进 Claude Code 的 AI 辅助层，使 AI 能够理解项目上下文、执行代码审查、触发测试和版本管理等工作流。

### 1.2 架构剖析

rtk 的 Claude Code 辅助层采用 **四层结构**：

| 层级 | 路径 | 文件数 | 职责 |
|------|------|--------|------|
| skill | `.claude/skills/` | 11 个 SKILL.md | 可复用的领域知识（pr-review、performance、security-guardian 等） |
| agent | `.claude/agents/` | 6 个 agent `.md` | 专职任务执行（rust-rtk、rtk-testing-specialist、technical-writer 等） |
| command | `.claude/commands/` | 4 + `tech/`子目录 6 = 10 个 | 用户入口（worktree 工作流、诊断、技术操作） |
| hook | 3 个路径（见下） | 3 个副本 | 工具调用拦截与重写 |

```
.claude/
  skills/         11 个 SKILL.md（pr-review, performance, repo-recap, ship,
                  security-guardian, code-simplifier, design-patterns,
                  rtk-tdd, tdd-rust, pr-triage, rtk-triage, issue-triage）
  agents/         6 个 agent md（rust-rtk, rtk-testing-specialist,
                  technical-writer, system-architect, debugger, code-reviewer）
  commands/       worktree.md, clean-worktree.md, worktree-status.md,
                  test-routing.md, clean-worktrees.md, diagnose.md
                  tech/（codereview, commit, deploy, docs, merge, worktree）
  hooks/          rtk-rewrite.sh
.github/hooks/    rtk-rewrite.json（非标准路径！）
hooks/claude/     rtk-rewrite.sh（第 3 个副本）
install.sh        CLI 安装脚本（curl-pipe-sh 注释）
scripts/          benchmark.sh（含 eval！）、test-all.sh、
                  update-readme-metrics.sh
```

hook 文件在三个路径各存一份：只有 `.claude/hooks/` 下的副本会被 Claude Code 自动加载，另外两处是孤立副本，形成维护分歧风险。

### 1.3 设计思路 / 方法论

**"worktree 优先型开发 + AI 辅助层"** 是 rtk 最鲜明的设计哲学。

命令层中存在大量 worktree 相关命令（`worktree.md`、`clean-worktree.md`、`worktree-status.md`、`clean-worktrees.md`，`tech/worktree.md`），暗示项目团队的主要工作流是**并行 worktree 驱动的**——不同功能分支各占一个 worktree，互不干扰。rtk-triage、pr-triage、issue-triage 三个 skill 进一步将分诊逻辑沉淀为可复用知识，让 AI agent 能够在不同 worktree 中统一执行 PR/issue 处理策略。

这一设计思路解决了一个实际张力：大型 Redux Toolkit 项目往往需要同时维护多个 feature 分支，手动切换分支会中断开发上下文。通过 worktree + AI 辅助层，作者试图让 AI 充当「多分支上下文切换的代理人」。

## 二、架构作为可学习模式（横向）

### 2.1 模式归类

**模式名：worktree 优先型开发 + 分层 AI 辅助（Worktree-First AI Overlay）**

核心特征：

- **命令层以 worktree 为主轴**：10 个 command 中有 5 个直接涉及 worktree 生命周期，表明并行分支开发是一等公民工作流，而非边缘场景
- **skill 层做分诊路由**：rtk-triage、pr-triage、issue-triage 三个 skill 承担「输入分类 → 路由到正确 agent」的职责，是典型的 [router-channels](#术语表) 模式
- **agent 按角色专职化**：6 个 agent 各自对应一类工程师角色（测试专家、技术作家、系统架构师、调试员、代码审查员），而非按功能划分
- **hook 统一做输入重写**：`rtk-rewrite.sh` 在工具调用入口拦截并重写输入，集中处理命名约定校正，实现 [single-purpose](#术语表) 原则

### 2.2 适用场景

- 大型前端项目同时维护多个 feature 分支，需要 AI 在不同 worktree 间快速切换上下文
- 项目有明确的角色分工（前端、后端、测试、文档），可以对应 agent 的角色专职化
- 需要统一输入命名规范（如 Redux action 名称、slice 文件命名），适合用 hook 层集中重写

### 2.3 与其他架构对比

| 维度 | rtk-ai/rtk（worktree 优先） | 典型单分支项目 | ruflo（swarm 编排） |
|------|----------------------------|---------------|-------------------|
| 并行分支策略 | worktree 作为一等工作流 | `git stash` 切换 | 并发 Agent 池 |
| skill 路由 | 分诊 skill（triage） | 无路由层 | swarm coordinator |
| Agent 专职化 | 按工程师角色 | 通用 Agent | 按任务阶段 |
| Hook 职责 | 输入重写（单一职责） | 无 hook 或多职责 | 生命周期回调 |

### 2.4 改进空间

1. **hook 文件存在于三个路径（.claude/hooks/、.github/hooks/、hooks/claude/），只有第一个自动加载**：其余两处副本形成了「维护幻觉」，修改主副本时容易遗忘同步，建议删除 `.github/hooks/` 和 `hooks/claude/` 下的副本，或改为符号链接指向 `.claude/hooks/rtk-rewrite.sh`

2. **worktree.md 和 tech/worktree.md 近乎重复（CC-1）**：两个文件覆盖几乎相同的内容（根目录版 vs tech/ 子目录版），建议合并为单一文件，让 tech/ 目录的版本用 `include` 或明确 cross-reference 指向根目录版本

3. **5 个 skill 缺失 `name` 字段，导致 skill 不可被按名引用（BUG-1）**：这是 88/100 分最核心的拖分原因，单次修复影响最大

### 3.2 当时值得借鉴的模式

**1. rtk-triage/SKILL.md 的 98 分结构（最高分 skill）**

`rtk-triage/SKILL.md` 是全库评分最高的制品（98 分），仅扣 2 分用于轻微模糊量词。其值得学习之处：

- **分诊逻辑显式化**：skill 正文明确列出了「接收 RTK issue 输入 → 分类（bug/feature/question）→ 路由到对应处理流程」的决策树，每个分支有明确的操作步骤，无"视情况而定"之类的模糊处理
- **`name` 字段正确声明**：与同目录下 5 个缺失 `name` 的 skill 形成对比，rtk-triage 正确设置了 `name: rtk-triage`，可被其他 agent 和命令按名引用
- **边界条件有明确处理**：对于无法分类的输入，skill 指定了具体的 fallback 行为（而非"适当处理"）

**2. agent 角色专职化设计**

`technical-writer.md`（技术作家）拥有 `Write`、`Edit` 工具权限，而代码相关的 agent 则不包含这些写权限。这种按角色切分工具权限的设计确保了最小权限原则：测试 agent 不会意外写入文档，文档 agent 不会误触代码执行工具。

**3. hook 单一职责**

`rtk-rewrite.sh` 专注于一件事：拦截 Write/Edit/MultiEdit 工具调用，检测输入是否符合 RTK 命名规范，不符合时重写为标准命名。这是 [single-purpose hook](#术语表) 的良好范例——hook 职责边界清晰，不承担日志、指标收集等额外职责（相比之下，`hooks/claude/rtk-rewrite.sh` 第 30-35 行存在记录完整 `$CLAUDE_TOOL_INPUT` 的副作用，属于安全隐患）。

### 3.3 当时的缺陷

**BUG-1：5 个 skill 缺失 `name` 字段（核心问题）**

受影响文件：
- `.claude/skills/pr-review/SKILL.md`
- `.claude/skills/performance/SKILL.md`
- `.claude/skills/repo-recap/SKILL.md`
- `.claude/skills/ship/SKILL.md`
- `.claude/skills/security-guardian/SKILL.md`

缺失 `name` 字段的后果：Claude Code 无法通过 `use skill:pr-review` 等方式按名引用这些 skill；它们在 agent 的 `skills:` 声明中也无法被正确解析，只能作为上下文文件被动加载，失去了「按需调用」的能力。这是 [manifest-discipline](#术语表) 问题的典型表现——结构完整，元数据残缺。

**BUG-2：`scripts/benchmark.sh` 中的 `eval` 执行（CRITICAL 安全）**

第 47-48 行：

```bash
eval "$unix_cmd"
eval "$rtk_cmd"
```

`$unix_cmd` 和 `$rtk_cmd` 来自用户可控的命令行参数，直接 `eval` 等同于将任意代码注入 shell 执行器。任何调用 benchmark.sh 的自动化流程（CI、hook、脚本）都暴露在任意代码执行风险中。这是 rtk 被安全门阻断（BLOCKED）的直接原因之一。

**BUG-3：`install.sh` 的 curl-pipe-sh 安装方式（CRITICAL 安全）**

`install.sh` 第 3 行将 `curl https://... | bash` 作为官方推荐安装方式注释呈现，同时第 82 行下载二进制时无 sha256sum 校验。curl-pipe-sh 是已知的高风险安装范式：下载地址被劫持时，用户在无感知的情况下执行了攻击者控制的脚本。

**QI-1：12 个命令文件缺失 `allowed-tools` 声明**

10 个命令中有多数未声明允许的工具集合，导致 Claude Code 在执行命令时回退到默认工具集，无法按最小权限原则限制命令的操作范围。

**QI-5：命令文件中混入法语文本**

`test-routing.md`、`diagnose.md`、`tech/codereview.md` 中出现 `Étape 1:`、`Options de déploiement:` 等法语短语。这说明文件可能来自多语言贡献者的混合提交，或模板复制时未清理语言标记，在英语为主的项目中属于一致性缺陷。

**CC-2：hook 文件散落三处，仅一处自动加载**

| 路径 | 是否自动加载 |
|------|------------|
| `.claude/hooks/rtk-rewrite.sh` | 是（Claude Code 标准路径） |
| `.github/hooks/rtk-rewrite.json` | 否（非标准路径，且为 JSON 而非 sh） |
| `hooks/claude/rtk-rewrite.sh` | 否（非标准路径） |

三处副本不同步时，用户以为更新了 hook，实际修改的是未被加载的副本，形成静默失效。

**CC-3：版本号跨文件不一致**

`hooks/claude/rtk-rewrite.sh` 检查 `>= 0.23.0`，而 `CLAUDE.md` 引用 `0.28.2` 作为当前版本。版本检查未同步，会导致旧版本环境下的 hook 跳过执行，用户得不到预期的输入重写保护。

### 3.4 当时的优化机会

1. 为 5 个缺失 `name` 的 skill 补充 `name:` 字段——单次批量修复，影响最大（每个 skill 的 frontmatter 顶部添加一行，5 分钟内完成）
2. 将 `scripts/benchmark.sh` 中的 `eval "$unix_cmd"` 替换为参数白名单验证 + 数组展开，消除任意代码执行路径
3. 为 `install.sh` 的二进制下载步骤添加 sha256sum 验证，替换 curl-pipe-sh 注释为带校验的安装方式
4. 删除 `.github/hooks/rtk-rewrite.json` 和 `hooks/claude/rtk-rewrite.sh` 两个孤立副本（或改为符号链接）

## 五、校准

### 5.1 我已经在做对的

1. **hook 路径规范**：将 hook 文件统一放置在 `.claude/hooks/` 下（Claude Code 标准路径），避免 rtk 这种三处副本、只有一处被加载的问题。如果我的项目 hook 完全在 `.claude/hooks/` 内，这是比 rtk 更规范的做法

2. **skill `name` 字段意识**：如果我的 skill 文件都声明了 `name:` 字段，就避免了 rtk 中 5 个 skill 不可按名引用的问题。这是 manifest-discipline 的基本要求

3. **不在脚本中使用 `eval` 执行用户输入**：rtk 的 `benchmark.sh` 中 `eval "$unix_cmd"` 是 CRITICAL 安全问题。如果我的脚本在处理外部输入时使用参数数组而非字符串 `eval`，则在安全实践上优于 rtk

### 5.2 挑战 / 验证

1. **挑战：`allowed-tools` 格式细节**：rtk 中 3 个 skill 的 `allowed-tools` 使用空格分隔而非 YAML 列表。这是容易被忽视的格式差异——两种写法在部分场景下均能解析，但语义不同，可能在工具执行时产生意外行为。验证方式：
   ```bash
   grep -n 'allowed-tools:' .claude/skills/*/SKILL.md .claude/agents/*.md 2>/dev/null
   ```
   命中后检查每个 `allowed-tools:` 后面是空格分隔字符串还是 `- tool-name` 列表格式

2. **挑战：hook 副本的隐性风险**：rtk 的案例提醒我，在项目演进过程中，hook 文件可能因不同贡献者放错路径而产生孤立副本。即使自己维护规范，也需要定期扫描确认没有遗漏的副本：
   ```bash
   find . -name "*.sh" -path "*/hooks/*" -o -name "hooks.json" 2>/dev/null | grep -v ".git"
   ```

3. **验证：worktree 命令的 `$ARGUMENTS` 空输入检查**：rtk 的 `worktree.md` 和 `tech/worktree.md` 缺乏对 `$ARGUMENTS` 为空时的检查，会在用户不传参数时产生模糊错误。检查我的命令文件是否有空输入防护：
   ```bash
   grep -L '\$ARGUMENTS' .claude/commands/*.md .claude/commands/**/*.md 2>/dev/null
   ```

```bash
for f in $(find .claude/commands/ -name "*.md" 2>/dev/null); do
  if grep -q '\$ARGUMENTS' "$f" && ! grep -q 'if.*ARGUMENTS\|ARGUMENTS.*-z\|-z.*ARGUMENTS' "$f"; then
```


### 6.2 灵感 → 实施路径

**灵感 1：学习 rtk-triage/SKILL.md（98 分）的分诊结构**

## 八、术语表

| 术语 | 解释 |
|------|------|
| **artifacts（制品）** | 在 NLPM 语境下，指用自然语言写成、供 AI agent 或开发者使用的结构化文本文件，如 SKILL.md、agent `.md`、command `.md`、CLAUDE.md 等 |
| **skill** | Claude Code 体系中的技能定义文件（通常为 SKILL.md），声明 AI agent 应如何完成某类任务的 frontmatter + 正文结构 |
| **agent** | Claude Code 体系中的智能体定义文件（通常为 `<name>.md`），声明执行特定角色任务的 AI 实体，包含模型、工具权限、工作流等 |
| **frontmatter** | Markdown 文件开头以 `---` 包裹的 YAML 元数据块，用于声明 `name`、`model`、`tools`、`allowed-tools`、`description` 等机器可读属性 |
| **manifest-discipline（清单纪律）** | 保持 frontmatter 字段完整、格式规范、值准确的工程习惯；rtk 的 5 个 skill 缺失 `name` 字段是 manifest-discipline 不足的典型表现 |
| **curl-pipe-bash-risk** | 将 `curl <url> | bash` 作为安装方式的安全风险；下载内容被中间人篡改时，用户会在无感知的情况下执行攻击者的代码 |
| **eval 注入** | 在 shell 脚本中将用户可控的变量内容传给 `eval` 执行，导致任意代码可被注入并执行；rtk 的 `benchmark.sh` 第 47-48 行是典型案例 |
| **vague-quantifier（模糊量词）** | 不提供可操作定义的形容词或副词，如 `ensure`、`appropriate`、`relevant`、`properly`；AI agent 遇到这类词语需要自行解释，导致执行结果不一致 |
| **router-channels（路由通道）** | 通过分诊 skill（triage skill）将不同类型的输入路由到专职 agent 或处理流程的模式；rtk 的 rtk-triage、pr-triage、issue-triage 是典型实现 |
| **single-purpose hook** | 仅承担单一职责的 Claude Code hook；rtk 的 `rtk-rewrite.sh` 专注于输入命名重写，是此模式的良好范例 |
| **worktree** | Git 的并行工作目录机制（`git worktree add`），允许同一仓库的不同分支在文件系统中以独立目录并行存在；rtk 将 worktree 管理作为主要工作流的一等公民 |
| **allowed-tools** | SKILL.md 和 agent `.md` frontmatter 中声明 AI 可以调用的工具白名单；应为 YAML 列表格式（`- Read`），而非空格分隔字符串（`Read Write`） |
| **cross-reference（交叉引用）** | skill 或文档中指向其他文件的引用；NLPM Audit 验证所有引用目标是否真实存在 |
| **BLOCKED（安全阻断）** | NLPM 安全扫描结果之一；含 Critical 级安全发现时触发，自动阻止贡献流水线向目标仓库提交 PR |
| **CLAUDE.md** | Claude Code 的项目记忆文件，存放在仓库根目录，向所有 Claude Code 会话提供项目上下文；rtk 的 CLAUDE.md 评分 88 分 |
| **cannot-verify** | 当无法访问目标仓库当前 HEAD 时，对缺陷当前状态的标注，表示无法确认是否已修复 |
| **probably-persists** | 当无法访问当前 HEAD，但基于技术合理性推断某缺陷极可能仍然存在时的状态标注 |
| **sha256sum 验证** | 下载二进制文件后，将其 SHA-256 哈希与发布者公布的期望值比对，确保文件未被篡改；rtk 的 `install.sh` 缺少此步骤 |
