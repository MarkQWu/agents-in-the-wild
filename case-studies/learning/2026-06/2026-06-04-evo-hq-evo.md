## 一、理解（基于当前仓库状态）

### 1.1 仓库概览
evo 是一个结构化实验驱动的代码优化插件，使用树搜索与并行子智能体对代码质量进行量化改进。当前版本 0.4.4，作者来自 evo-hq 团队，通过 Claude Code 插件市场分发（`claude plugin install evo@evo-hq`）。核心用法：给 Claude 一个待优化的函数/模块，evo 通过多轮实验迭代找到最优解。

关键事实：
- 支持本地/Modal/E2B/Daytona/AWS/Azure/SSH 等多种执行后端
- 内置 RLM（强化学习度量）评测框架，可量化优化效果
- 随附 SDK（Python + Node.js）供开发者内嵌 evo 协议到自己的基准测试

### 1.2 架构剖析

**目录结构**（关键部分）：
```
plugins/evo/
  .claude-plugin/plugin.json       # 插件清单
  skills/
    discover/SKILL.md              # 发现可优化维度
    discover/references/           # 6个参考文件（SDK、instrumentation示例）
    optimize/SKILL.md              # 树搜索优化循环
    optimize/references/           # sizing-the-round.md
    subagent/SKILL.md              # 并行子智能体执行
    infra-setup/SKILL.md           # 后端切换（非用户直接调用）
    report/SKILL.md                # 终端内渲染得分图（非用户直接调用）
    references/                    # 共享参考（agent-sdk-reference, cli-quick-reference）
sdk/
scripts/rlm_eval/                  # 评测脚本
```

**文件类型分布**：5 个 SKILL.md（3 个用户可调用 + 2 个引用型）/ 0 个 command / 0 个 agent / 1 个 plugin.json

**编排关系**：`discover` → `optimize`（多轮）→ `subagent`（并行）→ `report`（可选）。optimize 调用 subagent 执行具体实验；infra-setup 是 optimize/subagent 的非用户 setup 参考。是分层调用（有明确的顶层/底层职责），不是平列关系。

**跨件契约**：SKILL.md 通过 `references/` 目录引用内嵌代码模板（`inline_instrumentation.py/.js`、`sdk_python.py`）和协议文档（`instrumentation-contract.md`）。optimize 的 `references/sizing-the-round.md` 决定实验轮次预算。引用全部是相对路径，由 Claude Code 在 skill 加载时解析。

### 1.3 设计思路 / 方法论

**核心设计哲学**：「内联文档即可执行合同」——每个 skill 不仅是指令，还附带 references/ 子目录里的真实可运行代码，Claude 读 skill 时同步拿到示例实现。

**解决什么问题**：AI 辅助优化缺乏可重复性和可量化性——随机试了几次就结束，没有真正的树搜索，没有度量指标跟踪。evo 把「优化」变成「有界实验循环」。

**做了什么 trade-off**：重度依赖结构化协议（`EVO_TRACES_DIR`、`EVO_RESULT_PATH` 环境变量）→ 上手成本高，但确保每次实验结果可以被工具链追踪和比较。放弃了「简单 prompt 即用」的便利，换取了可审计性。

**反映什么认知模型**：作者认为 LLM 应当是「可控实验者」而非「一次性建议者」——优化效果必须可测量，不可测量的改进不算改进。

## 二、架构作为可学习模式（横向）

### 2.1 模式归类
**「Skills-as-Protocol + 内联参考资料」模式**：每个 skill 是一份 NL 合同，合同附带可执行的参考实现（`.py`/`.js` 文件），Claude 加载 skill 时同时获得协议文档和代码示例，无需在对话中重新解释。

模式特征清单：
- 特征 1：`references/` 子目录直接挂在 SKILL.md 旁边，路径约定一致
- 特征 2：引用文件包含真实可运行代码（不只是文档说明）
- 特征 3：有「不可用户调用」skill（infra-setup、report），职责分离清晰
- 特征 4：共享 references 放在 `skills/references/`，组件级 references 放在各自子目录
- 特征 5：plugin.json 不枚举 skills，依靠目录约定发现——降低清单维护负担

### 2.2 适用场景

| 场景 | 适不适用 | 原因 |
|---|---|---|
| 需要把算法实现示例内嵌到 skill 的工具性插件 | ✅ 高度适用 | references 机制天然支持代码 + NL 并存 |
| 纯 NL 交互（无代码参考）的 skill | ❌ 过度设计 | references 目录带来文件管理成本，无实际收益 |
| 有多个后端选项需要运行时切换的场景 | ✅ 适用 | infra-setup 非用户调用 skill 的模式可复用 |
| 5 个以上同等地位 skill 的插件 | ⚠️ 注意 | discover→optimize→subagent 的有序调用链是本模式收益来源；平列 skill 用这个模式收益有限 |

### 2.3 与其他架构对比

| 架构 | 典型代表 | 优势 | 劣势 |
|---|---|---|---|
| Skills-as-Protocol + 内联参考资料（本仓库） | evo-hq/evo | 代码示例随 skill 一起载入，减少对话中解释 | 目录结构复杂；更新参考代码不触发 skill 变更 |
| 纯 NL skill（无引用文件） | antfu/skills | 最简单，易维护 | 算法/实现细节靠模型记忆，不稳定 |
| 经验侧车（experience_digest）模式 | 0xmariowu/Autosearch | 运行时累积经验，跨会话学习 | 需要运行时写文件，静态参考 skills 无法用 |

### 2.4 改进空间
1. **当前问题**：`"handful"`、`"meaningfully different"` 仍是模糊量词（audit 后未修复）**改进做法**：discover/SKILL.md:94 改 `A handful of dimensions` → `3–6 个维度`；optimize/SKILL.md:227 改 `meaningfully different framings` → `至少一个不同的实现策略（如不同算法复杂度、不同数据结构）` **预期收益**：消除模型歧义，提高 discover 输出稳定性

2. **当前问题**：plugin.json 没有 `skills` 字段列表，依靠目录发现 **改进做法**：明确枚举 5 个 skills（含 disable-model-invocation 的）到 plugin.json，让清单成为权威来源 **预期收益**：方便工具链和 CI 检测孤立文件，减少「删了 skill 文件但清单没更新」的静默错误

## 八、术语表

### <a name="frontmatter"></a>frontmatter
> Markdown 文件最顶部用 `---` 包起来的一段 YAML 配置，用来声明文件的元数据（如 `name`、`description`、`disable-model-invocation` 等）。Claude Code 读 SKILL.md 时先解析 frontmatter 才能知道这个 skill 怎么注册和触发。

### <a name="RLM"></a>RLM（强化学习度量）
> Reinforcement Learning Metric，evo 用来量化每次代码优化效果的评分机制。简单说就是「给定一个基准测试，测优化前后得分差」，让「代码变好了」有一个客观数字，而不是「感觉好像快了」。

### <a name="disable-model-invocation"></a>disable-model-invocation
> SKILL.md frontmatter 里的一个字段，值为 `true` 时表示这个 skill 不应该被用户直接通过 `@skill-name` 触发，而是作为被其他 skill 或 command 间接调用的工具性组件。类似于代码里的 `private` 函数——对外不可见，对内可用。
