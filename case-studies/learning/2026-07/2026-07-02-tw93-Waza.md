## 一、理解（基于当前仓库状态）

### 1.1 仓库概览
**tw93/Waza** 是一个精简的 Claude Code 技能集，由开发者 tw93（潮流周刊 Pake 作者）创作，理念是「把工程师已有的工程习惯变成 AI agent 可执行的技能」。共 8 个技能，每个技能「做且仅做一件事，完成后停下，等你决定下一步」。

关键事实：
- 作者 tw93 是知名中国开发者，代表作有 Pake（GitHub 22k+ stars）和潮流周刊，个人技术品味极高
- 安装方式：`npx skills` 或通过 claude-code action 自动配置
- 8 个技能覆盖：`/think`（设计预压测）、`/ui`（界面设计）、`/check`（diff 审查）、`/hunt`（系统化调试）、`/write`（中英文写作）、`/learn`（快速研究）、`/read`（URL/PDF 处理）、`/health`（AI agent 健康审查）
- 3301 stars，是「个人品味驱动」的小而美风格
- 审计评分 79/100（因 4 个 agent 文件完全无 [frontmatter](#frontmatter) 拉低均值），9 个 skill/CLAUDE.md 文件均在 96-98 分

### 1.2 架构剖析
- **目录结构**：
  ```
  Waza/
  ├── skills/
  │   ├── RESOLVER.md              # 技能路由说明（机械化检查覆盖）
  │   ├── think/SKILL.md           # 设计预压测
  │   ├── ui/SKILL.md              # 界面设计
  │   ├── check/
  │   │   ├── SKILL.md             # diff 审查主 skill（97分）
  │   │   └── agents/
  │   │       ├── reviewer-architecture.md  # 架构审查 agent（38分！）
  │   │       └── reviewer-security.md      # 安全审查 agent（38分！）
  │   ├── health/
  │   │   ├── SKILL.md             # agent 健康审查主 skill（96分）
  │   │   └── agents/
  │   │       ├── inspector-context.md      # 上下文检查 agent（38分！）
  │   │       └── inspector-control.md      # 控制检查 agent（40分！）
  │   ├── hunt/ learn/ read/ write/ design/ # 其他 skill（均 98分）
  │   └── （支持文件：persona-catalog.md, design-reference.md 等）
  ├── scripts/
  │   ├── setup-statusline.sh      # 安装脚本（存在 HIGH 安全风险）
  │   ├── statusline.sh            # 状态行脚本
  │   └── verify-skills.sh        # 自动质量验证脚本
  └── CLAUDE.md                    # 项目说明（98分）
  ```
- **文件类型分布**：8 个 SKILL.md + 1 个 CLAUDE.md + 4 个 agent 文件 = 13 个 NL 工件；3 个 shell 脚本
- **编排关系**：`check/SKILL.md` 和 `health/SKILL.md` 均调用 `agents/` 子目录中的 agent 文件作为并行子 agent；RESOLVER.md 是 8 个 skill 的路由说明，由 `verify-skills.sh` 机械验证存在性
- **跨件契约**：`verify-skills.sh` 强制要求每个 SKILL.md 在 RESOLVER.md 中有对应条目；该脚本同时验证所有支持文件（persona-catalog.md 等）存在。BUT：4 个 agent 文件不在 `verify-skills.sh` 的验证范围内，质量问题因此长期无人发现

### 1.3 设计思路 / 方法论
- **核心设计哲学**：「克制即美」——拒绝大而全，每个技能只做一件事，执行完就停，等人决定下一步。8 个技能对应 8 个「真正重要的工程习惯」
- **解决什么问题**：AI coding assistant 的输出质量参差不齐，根本原因是缺乏结构化约束；Waza 通过强 trigger condition + 清晰 scope 限制每个技能的边界
- **做了什么 trade-off**：选择「少量精品」而非「大量普通」——8 个技能经过作者深思熟虑，每个都有明确的「不适用场景」；代价是不能快速扩展（每新增一个技能都需要严格论证）
- **反映什么认知模型**：作者相信 AI 的最大价值在于「可重复执行有明确边界的任务」，而不是「开放式推理」；技能越聚焦，AI 越可靠

## 二、架构作为可学习模式（横向）

### 2.1 模式归类
**模式名：「精品技能 + 自动化验证门卫」（Curated Skills + Mechanical Quality Gate）**

作者不追求技能数量，而是用 `verify-skills.sh` 脚本作为质量门卫：在提交时自动验证所有 SKILL.md 在 RESOLVER.md 中有对应条目、所有引用文件存在。这是一种「代码 review 外包给脚本」的质量维护策略。

模式特征清单：
- 特征 1：`RESOLVER.md` 作为路由文件，明确每个技能的触发条件和不适用场景
- 特征 2：`verify-skills.sh` 机械化检查 RESOLVER.md 覆盖率、引用文件存在性
- 特征 3：每个技能有明确的「Not for」排除子句
- 特征 4：质量验证覆盖 SKILL.md，但未覆盖 agents/ 子目录——形成质量盲区
- 特征 5：技能设计上的刻意克制：8 个技能已经考虑得很深，不轻易扩展

### 2.2 适用场景

| 场景 | 适不适用 | 原因 |
|---|---|---|
| 个人品牌驱动的工具（高质量小而美） | ✅ 高度适用 | 少量精品比大量平庸更能体现作者价值观 |
| 需要跨项目重复使用的通用工程习惯 | ✅ 适用 | 8 个技能都是领域无关的工程最佳实践 |
| 需要覆盖特定业务领域（如 PostgreSQL） | ❌ 不适用 | Waza 的设计故意避开垂直领域，是通用工程方法 |
| 需要快速扩展技能集的团队 | ❌ 不适用 | 精品设计不支持快速膨胀，verify-skills.sh 形成了扩展摩擦 |

### 2.3 与其他架构对比

| 架构 | 典型代表 | 优势 | 劣势 |
|---|---|---|---|
| 精品技能 + 自动质量门卫（本仓库） | tw93/Waza | 质量高且一致，验证可自动化 | 扩展慢，验证盲区（agents/）导致低质量组件漏网 |
| 多插件 Monorepo | team-attention/plugins-for-claude-natives | 覆盖面广，功能丰富 | 质量参差不齐（70～100 分的跨度） |
| 单一大型 skill | pg-aiguide (postgres/SKILL.md) | 集中控制 | 单点故障（一处 bug = 整个 skill 失效） |

### 2.4 改进空间
1. **当前问题**：`verify-skills.sh` 验证覆盖 SKILL.md 但不覆盖 `agents/` 子目录，导致 4 个 agent 文件以 38-40 分的状态长期存在。**改进做法**：扩展 `verify-skills.sh` 添加 lint 逻辑：检查所有 `agents/*.md` 文件是否有 `name`、`description`、`model` frontmatter 字段。**预期收益**：4 个 agent 文件得分从 38 升至 80+，RESOLVER.md 的覆盖也可扩展到 agents。
2. **当前问题**：`setup-statusline.sh` 下载脚本后不验证 SHA-256 完整性（已将 branch 改为 tag，但仍无哈希校验）。**改进做法**：在 curl 下载后添加 `echo "<预期SHA256>  $DEST" | sha256sum -c || { rm "$DEST"; exit 1; }`。**预期收益**：即使 GitHub raw 内容被中间人篡改，用户也能通过校验失败发现。
3. **当前问题**：4 个 agent 文件（reviewer-architecture、reviewer-security、inspector-context、inspector-control）无任何 frontmatter，38 分。**改进做法**：为每个文件添加标准 frontmatter（`name`、`description`、`model`、至少 1 个 `<example>` 块）。**预期收益**：总体评分从 79 升至约 95，且这些 agent 文件可以被工具机械化质量检查。

| 文件 | 当时分数 | 主要问题 |
|---|---|---|
| skills/check/agents/reviewer-architecture.md | 38 | 无 frontmatter（name/description 各 -25），无 model（-5），只有 1 个 example（-5） |
| skills/check/agents/reviewer-security.md | 38 | 同上 |
| skills/health/agents/inspector-context.md | 38 | 同上 |

| skills/check/SKILL.md | 97 | 「obvious」1 次（-2） |
| CLAUDE.md | 98 | 「non-trivial」1 次（-2） |

**关键观察**：79/100 的评分由 4 个 agent 文件单独拉低；9 个 SKILL.md/CLAUDE.md 的均分为 97.6 分——这是当前 207 个审计仓库中最高的 NL skill 质量平均分之一。

### 3.2 当时值得借鉴的模式

1. **verify-skills.sh 自动化质量门** → 在每次提交前自动验证 RESOLVER.md 覆盖率、版本一致性、引用文件存在性。根本原因：机械可验证的检查永远比「依赖人工记得」更可靠。如何借鉴：为自己的 skill 仓库写一个 pre-commit 脚本，哪怕只检查「所有 SKILL.md 都有 frontmatter 中的 name 字段」。

2. **RESOLVER.md 技能路由 + Not for 排除子句** → 每个技能在 RESOLVER.md 中有 trigger condition 和「不适用场景」两个字段。根本原因：让 AI 和用户都知道何时「不该」用某个技能，比只说「何时该用」更有价值。如何借鉴：在自己的 SKILL.md 的 description 中加 `Not for: <反例>`。

3. **技能克制设计（做完就停）** → 8 个技能均不自动触发下一步，执行完等用户决策。根本原因：避免 agent chain 中一个错误决策链式放大。如何借鉴：设计 skill 时明确「交付物是什么，然后停」，而不是「然后继续做 X Y Z」。

4. **API 废弃表 + 版本感知** → `setup-timescaledb-hypertables/SKILL.md` 包含废弃 API 对照表（虽然这是 pg-aiguide 的特点，Waza 的 hunt/SKILL.md 有类似的系统化调试步骤固化）。如何借鉴：把「高度结构化的专业步骤」以枚举列表形式固化在 skill 中，AI 不需要自己「摸索步骤」。

5. **并行子 agent 模式**（check/health → agents/）→ `check/SKILL.md` 将 diff 同时发给 `reviewer-architecture` 和 `reviewer-security` 两个专业 agent 并行审查，最终综合结论。根本原因：架构 review 和安全 review 是正交维度，并行比串行效率高，且互相不干扰。如何借鉴：当一个任务有多个独立审查维度时，设计并行子 agent 而非单一全能 agent。

### 3.3 当时的缺陷

1. **HIGH 安全 — `setup-statusline.sh` 下载脚本无版本固定**（审计时指向 main 分支）→ 用户运行安装脚本时，curl 从 `main` 分支下载 `statusline.sh` 并立刻 chmod +x 执行，无任何完整性验证。若 GitHub 账号被盗或 main 分支被篡改，所有用户的 `~/.claude/` 都会被注入恶意代码。**根本原因**：作者直觉上使用「拉最新版」的便利性，未考虑 `main` 分支是可变的供应链攻击面。这是 `curl|bash` 类反模式的典型变种。**自查**：我的 setup/install 脚本中有没有从远端拉代码然后直接执行的环节？

2. **4 个 agent 文件完全无 frontmatter**（reviewer-architecture/security，inspector-context/control）→ 这些文件作为「原始系统提示词」传给子 agent，没有 `name`、`description`、`model` 字段，不可被工具机械化检查，且没有 `<example>` 块展示期望输出。**根本原因**：`verify-skills.sh` 的验证范围只覆盖 SKILL.md，agent 文件游离在质量控制体系外。验证盲区 + 没有人工习惯检查 = 长期低质量。**自查**：我的仓库中是否有被质量自动化检查遗漏的文件类型？

3. **verify-skills.sh 验证盲区**（agents/ 子目录未被覆盖）→ 脚本在保证 SKILL.md 质量方面做得极好，但形成了一个「只要不是 SKILL.md 就不会被检查」的盲区。**根本原因**：脚本是增量演化的，最初只有 SKILL.md，后来增加了 agents/ 但脚本没有跟着扩展。**自查**：我的 pre-commit 钩子覆盖了仓库中所有 NL 工件类型吗？

### 3.4 当时的优化机会

1. **将 main 分支 URL 固定为 tag URL 并添加 SHA-256 校验**：将 `setup-statusline.sh` 中的 curl 目标从 `main` 分支改为 `v3.11.0`（当时最新 tag），并在下载后加 SHA-256 验证。这是 HIGH 级别安全修复，代价极低（2 行改动）。
2. **为 4 个 agent 文件添加 frontmatter**：每个文件加 `name`、`description`、`model: sonnet`、1 个 `<example>` 块，将评分从 38 升至 80+，将仓库总分从 79 升至约 94。
3. **扩展 verify-skills.sh 覆盖 agents/**：添加一个循环检查所有 `agents/*.md` 是否有 `name:` 和 `description:` frontmatter 字段，防止此类低分 agent 文件再次产生。

|---|---|---|---|
| HIGH 安全：setup-statusline.sh 指向 main 分支 | WebFetch scripts/setup-statusline.sh，检查 WAZA_REF 变量 | **已部分修复** — 现在默认使用 `v3.30.0` tag（`WAZA_REF="${WAZA_REF:-v3.30.0}"`），且验证格式为 `v[0-9]*.[0-9]*.[0-9]*` 的语义版本。**但 SHA-256 验证仍缺失**，curl 下载后没有完整性校验 | 从 HIGH 降为 MEDIUM：供应链攻击从「任何 main 分支 push」降为「需要污染特定 tag 的 release」，安全性大幅提升；但仍需信任 HTTPS + GitHub 安全性，不够 paranoid 级别 |

### 4.2 架构演进
最重要的变化是 `setup-statusline.sh` 的安全修复：从硬编码 `main` 分支 URL 改为使用 `WAZA_REF` 变量（默认 `v3.30.0`），且允许用户覆盖（如 `WAZA_REF=main`）。这说明作者在 HIGH 安全发现后进行了认真修复——从「完全无版本控制」到「有明确的 tag 默认值 + 格式验证」。版本号从 v3.11.0 升至 v3.30.0（增加 19 个 minor 版本），说明 Waza 在持续活跃开发中。

### 4.3 新增的可学习模式
`WAZA_REF` 变量的设计是一个值得借鉴的模式：`WAZA_REF="${WAZA_REF:-v3.30.0}"` 提供了默认 tag 同时允许用户覆盖（如 `WAZA_REF=main` 用于开发调试）。这是「安全默认 + 灵活覆盖」的经典模式——安全配置是默认值，危险操作需要用户明确 opt-in。

## 五、校准

### 5.1 我已经在做对的
1. **技能克制** — gstack 的 23 个命令各有明确职责，没有「通用助手」类的模糊命令
2. **output format 明确** — bureau 的 query.md 有详细的 Output Format 节和 Sources 列表规范
3. **安全 opt-in** — bureau 的信任层级（proposed/verified/canonical）是一种信息发布的 opt-in 机制
4. **Not for 意识** — bureau 的核心设计决策之一是「人工审批是门槛，不是可选项」，这是一种内置的排除子句

### 5.2 挑战 / 验证
**验证了我的一个判断**：「安全门的代价不是在于修复成本，而在于发现成本」。Waza 的 HIGH 安全问题（main 分支下载 + chmod +x）是 2 行代码的修复，但发现它需要有 NLPM 这样的安全扫描工具。这验证了「自动化安全扫描在 NL 工件中同样重要」——人类审阅者很少会想到检查 curl 的下载来源是否有版本固定。

**挑战了我的假设**：我之前以为「开源 setup 脚本的 curl 下载是行业标准，不是安全风险」。但这个案例展示了：即使是个人开发者的「小工具」，只要有 curl→chmod→execute 的链条，就存在供应链攻击面。Waza 的修复（v tag + 版本格式验证）是务实的最优解。

### 7.3 别人的更优方案

1. **领域**：自动化质量门卫（verify-skills.sh 模式）
   - **本案例做法**：`scripts/verify-skills.sh` 在每次提交前自动验证 RESOLVER.md 覆盖率、版本号一致性、引用文件存在性
   - **我的项目现状**：gstack 和 bureau 目前均无 verify 脚本或 CI 检查（从 my-repos.json 的描述无法确认）
   - **如何借鉴**：在 gstack 创建 `scripts/verify.sh`，至少检查：(1) 所有 SKILL.md 有 `name:` 和 `description:`；(2) CLAUDE.md 中的所有文件路径引用存在。把脚本加进 `.git/hooks/pre-commit`，20 分钟

2. **领域**：RESOLVER.md 路由 + Not for 排除子句
   - **本案例做法**：RESOLVER.md 为每个技能规定 trigger condition（触发条件）和「不适用场景」，Claude 根据此路由
   - **我的项目现状**：gstack 的 23 个命令可能没有统一的路由说明文件（每个 command 的 description 是路由信息，但分散在各文件）
   - **如何借鉴**：在 gstack 创建 `RESOLVER.md`，用表格形式列出 23 个命令的触发条件和「不要在 X 时使用」，帮助 AI 正确路由，30 分钟

### 7.4 反向：我的项目做得比他们好的地方

- **领域**：质量自动化覆盖完整性（不留盲区）
- **我的做法**：bureau 的设计中，trust tier 规则适用于所有内容（notes、pages、logbook），没有「这种文件不受规则约束」的豁免区
- **本案例做法（弱在哪）**：`verify-skills.sh` 覆盖 SKILL.md 但遗漏了 `agents/` 子目录，导致 4 个 agent 文件以 38 分的状态长期存在——这正是盲区验证漏洞的典型体现
- **意义**：任何质量控制系统都应该问自己「什么类型的文件/代码不受这个控制？为什么？」。如果没有好的理由，就应该扩展覆盖。这个原则在 bureau 的信任体系中体现为：所有 AI 生成内容默认 proposed 状态，没有豁免。

## 八、术语表

### <a name="frontmatter"></a>frontmatter
> Markdown 文件最顶部用 `---` 包起来的一段 YAML 配置，声明文件的元数据（如 `name`、`description`、`model`、`color` 等）。Claude Code 读 agent/SKILL.md 时先解析 frontmatter 才能知道这个文件是什么、怎么注册和调用。缺少 frontmatter 的 agent 文件对工具来说是「不可发现的原始文本」。

### <a name="curl-pipe-bash-risk"></a>curl|bash 反模式（supply chain risk）
> 脚本从远端 URL 下载可执行内容并立即运行的模式（如 `curl https://... | bash` 或 `curl https://... -o file && chmod +x file && ./file`）。风险在于：如果 URL 对应的远端内容被篡改（账号被盗、CDN 被劫持、中间人攻击），用户系统就会执行攻击者的代码。防御方式：固定版本 + SHA-256 校验。

### <a name="RESOLVER-md"></a>RESOLVER.md
> Waza 中的技能路由说明文件，列出每个技能的触发条件和不适用场景。Claude Code 可以通过这个文件判断「用户的需求应该路由到哪个技能」。被 `verify-skills.sh` 机械检查是否覆盖了所有 SKILL.md。

### <a name="pre-commit-hook"></a>pre-commit hook（提交前钩子）
> 在执行 `git commit` 之前自动运行的脚本。如果脚本返回非零退出码，commit 被阻止。常用于格式检查、lint、单元测试、NL 工件质量验证等。Waza 的 `verify-skills.sh` 设计成可以作为 pre-commit hook 运行，在每次提交时自动保证 SKILL.md 质量。

### <a name="sha256-verification"></a>SHA-256 校验
> 下载文件后，计算文件内容的 SHA-256 哈希值，与已知的预期哈希值对比。如果两者不同，说明文件被篡改或下载损坏，应立即拒绝使用。这是防御 curl|bash 反模式的关键补充措施——即使 URL 和版本都正确，也能发现内容层面的篡改。
