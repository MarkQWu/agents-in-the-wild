## 一、理解（基于当前仓库状态）

### 1.1 仓库概览
Ouroboros 是一个「规范先行 AI 开发工作流引擎」。它的核心理念来自苏格拉底式提问——在让 AI 开始构建之前，先通过对话澄清「真正要构建什么」。用户安装后通过 `ooo` 系列命令驱动一个 **Seed（规格文档）→ 执行 → 评估 → 演进** 的闭环。

关键事实：
1. **Python MCP 后端**：核心逻辑是 [PyPI 包](#pypi) `ouroboros-ai`，Claude Code 通过 [MCP](#mcp) 工具（`ouroboros_execute_seed`、`ouroboros_auto` 等）调用
2. **三层 NL 层**：21 个 SKILL.md + 13 个 command + 21 个 agent markdown，都是对 MCP 工具的 NL 调度器
3. **多语言支持**：有 README.md（英文）、README.zh-CN.md（中文）、README.ko.md（韩文），面向全球用户
4. **当前版本 0.26.0**（CLAUDE.md 注释中可见）
5. 在 GitHub 有 3,637 stars，是 Claude Code 插件生态里少数建立了完整工程循环的项目

### 1.2 架构剖析
- **目录结构**：
```
ouroboros/
├── skills/          # 21 个 SKILL.md（工作流技能）
├── commands/        # 13 个 command markdown（入口命令）
├── src/ouroboros/agents/  # 21 个 agent markdown（专家角色）
├── hooks/           # hooks.json（SessionStart + UserPromptSubmit + PostToolUse）
├── scripts/         # Python 脚本（session-start.py、version-check.py 等）
├── crates/          # Rust 二进制工具（辅助）
├── pyproject.toml   # Python 包配置
└── CLAUDE.md        # 开发者模式调度器（非最终用户文件）
```
- **文件类型分布**：21 个 SKILL.md / 21 个 agent .md / 13 个 command .md / 3 个 hook 条目
- **编排关系**：命令（`ooo seed`）→ 对应 SKILL.md → 调用 MCP 工具 → Python 后端执行。Agent markdown 文件定义专家角色，被 skills 在需要时显式引用（如 `skills/interview/SKILL.md` 引用 `socratic-interviewer` agent）
- **跨件契约**：CLAUDE.md 在开发模式下充当路由表，将 `ooo <cmd>` 映射到对应 SKILL.md。MCP 工具名在 `skills/run/SKILL.md` [frontmatter](#frontmatter) 中声明（`mcp_tool: ouroboros_execute_seed`）

### 1.3 设计思路 / 方法论
- **核心设计哲学**：「规范先行，执行在后」——先用 Socratic interviewing 让用户写出一份高质量的 Seed 文档（可验证的功能规格），然后才让 AI 动手构建
- **解决什么问题**：AI 直接执行模糊任务时失败率高，作者发现根本原因是需求不清晰。Ouroboros 强制一个「澄清 → 规格 → 执行」的流水线
- **Trade-off**：上手门槛较高（需要学习 `ooo` 命令体系 + 安装 MCP 后端），但执行成功率据作者测试显著提升
- **认知模型**：AI 是执行器，人类是规格撰写者。MCP 后端维护持久状态（[session](#session)），NL 层只做调度，不嵌入业务逻辑

## 二、架构作为可学习模式（横向）

### 2.1 模式归类
**模式名：NL 表皮 + Python MCP 核心（NL-MCP-Hybrid）**

这个仓库把 NL 能力（自然语言规格、调度、用户界面）和程序化能力（状态管理、版本追踪、工作流引擎）完全分离。NL 层（.md 文件）只做两件事：告诉 Claude 何时调用哪个 MCP 工具，以及如何向用户展示结果。所有真正的业务逻辑（Seed 解析、执行追踪、差异分析）都在 Python 包里。

模式特征清单（4 条）：
- 特征 1：每个 SKILL.md 有 `mcp_tool:` frontmatter 字段，明确声明要调用的底层工具
- 特征 2：CLAUDE.md 充当开发模式下的「路由表」，正式安装后由 plugin.json 替代
- 特征 3：MCP 后端维护跨会话状态；NL 层无状态，可随时更新而不破坏进行中的工作流
- 特征 4：Agent 文件只定义角色（Contrarian、Hacker、Judge），不包含工具调用逻辑

### 2.2 适用场景

| 场景 | 适不适用 | 原因 |
|---|---|---|
| 多步工作流、需要跨会话持久化状态 | ✅ 高度适用 | MCP 后端天然适合维护 session 状态 |
| 需要复杂 Python 计算（机器学习、文件解析）| ✅ 适用 | 将计算下沉到 Python，NL 层只调度 |
| 简单一次性查询或单命令工作流 | ❌ 过度工程 | 引入 MCP 安装成本，不值得 |
| 没有编程背景的用户需要零依赖使用 | ❌ 不适用 | 需要 `pip install ouroboros-ai` + MCP 配置 |

### 2.3 与其他架构对比

| 架构 | 典型代表 | 优势 | 劣势 |
|---|---|---|---|
| NL-MCP-Hybrid（本仓库）| Q00/ouroboros | 状态持久化、复杂计算能力强、NL 层轻薄可替换 | 安装复杂，调试需跨 NL 和 Python 两层 |
| 纯 NL 平铺（Pure-NL）| 0xfurai/claude-code-subagents | 零依赖安装，即装即用 | 无法跨会话记忆，复杂逻辑堆在 prompt 里难维护 |
| NL 编排 + 脚本后端 | echo-sleuth-for-claude | 折中：脚本可测试，无 MCP 注册复杂度 | 状态管理仍在文件系统，不如 MCP 灵活 |

### 2.4 改进空间
1. **当前问题**：21 个 agent 文件全部没有 [YAML frontmatter](#frontmatter)（无 `name:`/`description:`），Claude Code 无法自动发现这些 agent。**改进做法**：用一个脚本批量生成 frontmatter（agent 名从文件名推导，description 从文档第一段提取）。**预期收益**：agent 可以被 `@mention` 直接调用，不再依赖 skill 的显式引用
2. **当前问题**：`skills/setup/SKILL.md` 里的 agent/skill 计数（15 skills、9 agents）比实际（21/21）落后。**改进做法**：在 CI 中加一个计数校验脚本（读 skills/ 和 agents/ 目录，与 setup SKILL 中的数字比对）。**预期收益**：成功消息不再误导用户
3. **当前问题**：`skills/pm/SKILL.md` Step 4 使用 `pbcopy`（macOS 专用），Linux/Windows 用户静默失败。**改进做法**：检测 OS，Linux 用 `xclip`，Windows 用 `clip.exe`，或打印内容让用户手动复制。**预期收益**：跨平台可用

### 3.2 当时值得借鉴的模式

1. **CLAUDE.md 开发路由器** → 在安装插件前可通过直接 read SKILL.md 调试，开发体验极好 → `CLAUDE.md` 第 5-31 行 → 借鉴：我的仓库也可在 CLAUDE.md 里加一个「dev fallback」表，让不装插件的开发者也能用文件路径直接触发 skill

3. **明确的 dispatch-failure 协议** → `skills/auto/SKILL.md` 写道「如果 MCP 工具不可用，停止并报告，不要用手动步骤模拟」→ 这防止了 Claude 在工具缺失时「假装成功」→ 借鉴：在任何依赖外部工具的 skill 里加同样的 stop 声明

4. **三语 README** → `README.md`/`README.zh-CN.md`/`README.ko.md` 体现了真实的全球化需求 → 借鉴：面向中英双语用户时，文档国际化可以从 README 开始，不必等功能稳定

### 3.3 当时的缺陷

1. **全部 21 个 agent 缺 frontmatter**（`name` + `description` 字段全部缺失）→ 根本原因：作者把 agent 当作「内部实现细节」而非 Claude Code 可注册的组件，混淆了 MCP 后端 agent 角色（Python 类）和 NL agent 文件的概念 → 自查：我的 echo-sleuth agents/ 目录有完整 frontmatter ✓

2. **Curl-pipe-sh 安全问题**（`skills/setup/SKILL.md` 让 Claude 直接执行 `curl ... | sh`）→ 根本原因：开发者复制了常见的 uv 安装文档而没有评估它在 AI agent 上下文中的安全含义——Claude Code 会直接执行这行命令 → 自查：我的项目暂无此问题

3. **`skills/run/SKILL.md` MCP 工具名不一致**（frontmatter 声明 `ouroboros_execute_seed`，body 调用 `ouroboros_start_execute_seed`）→ 根本原因：代码演进时只改了 body，没有同步更新 frontmatter 声明 → 自查：我的 skills 没有 `mcp_tool:` frontmatter，所以没有这个漂移，但如果将来加 MCP 工具就需要注意

### 3.4 当时的优化机会

1. 为 21 个 agent 批量添加 frontmatter（`name`、`description`、`model`），优先级最高，能把 NL 分从 69 提升至约 84
2. 把 `skills/setup/SKILL.md` 里的 `curl | sh` 改为文档步骤（「请在终端执行以下命令」），而非让 AI 自动执行
3. 统一 `skills/run/SKILL.md` frontmatter 和 body 里的 MCP 工具名

## 八、术语表

### <a name="pypi"></a>PyPI
> Python 的「应用商店」。`pip install ouroboros-ai` 从这里下载 Python 包。类比：就像 npm 之于 Node.js 程序，PyPI 是 Python 程序的分发平台。

### <a name="mcp"></a>MCP（Model Context Protocol）
> Anthropic 制定的一个协议，让 Claude 能调用外部工具（如本地程序、API）。Ouroboros 通过 MCP 把 Python 后端的功能暴露给 Claude，Claude 调用 `ouroboros_execute_seed` 其实是在调用一个 Python 函数。类比：MCP 相当于 Claude 的「USB 接口」，外部工具通过这个接口接入。

### <a name="frontmatter"></a>frontmatter
> Markdown 文件最顶部用 `---` 包起来的一段 YAML 配置，用来声明文件的元数据（如 `name`、`description`、`model` 等）。Claude Code 读 SKILL.md 时先解析 frontmatter 才能知道这个 skill 怎么注册和调用。

### <a name="session"></a>session（工作会话）
> 一次 Claude Code 对话。Ouroboros 的 MCP 后端在对话之间（跨 session）保存工作状态，即使关闭终端重开也能恢复。这是它与纯 NL 工具的核心区别之一。

### <a name="seed"></a>Seed（规格文档）
> Ouroboros 工作流的核心产物——一份详细的功能规格文档，描述「要构建什么」的所有细节。由 `ooo interview` 命令通过 Socratic 问答生成，是 `ooo run`（执行）的输入。类比：程序员的需求文档 + 技术规格书的合体。
