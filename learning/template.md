# 学习案例模板

> 这是 Routine 生成学习案例时使用的模板。修改这个文件 = 修改未来所有案例的结构。
> 已生成的案例不会回填，需要按新模板重新生成的话单独触发。

---

## 模板使用说明（给 Routine 看）

1. 读完此文件后，按照下方「案例模板」的结构填写
2. 占位符用 `<…>` 标记，全部替换为具体内容
3. 所有 section 都要有，没内容也要明确写「暂无」或「N/A」+ 理由
4. **专有名词处理**：正文遇到读者可能不懂的技术名词（如「原生二进制核心」「manifest」「OIDC token」「frontmatter」等），第一次出现时用锚点链接 `[原生二进制核心](#原生二进制核心)`，并在文末「术语表」section 加对应词条。术语解释要面向**技术小白**（吴同学定位），不要技术黑话堆砌
5. 全部中文写作

## 案例模板

```markdown
# <OWNER>/<REPO> — 学习案例

**仓库**：https://github.com/<OWNER>/<REPO>
**Stars**：<N> | **来源**：<xiaolai upstream | 本地 audit>
**Audit 日期**：<YYYY-MM-DD>（历史快照）| **生成日期**：<YYYY-MM-DD>（基于当前 HEAD）
**主题标签**：<3-5 个逗号分隔的英文标签>

[如 xiaolai 写过该仓库的案例]：**xiaolai 案例**：[../<2026-MM-DD-slug>.md](../<2026-MM-DD-slug>.md)

## 一、理解（基于当前仓库状态）

### 1.1 仓库概览
一句话定位 + 3-5 个关键事实（创建时间 / 作者背景 / 用户获取方式 / 在生态中的位置）。

### 1.2 架构剖析
- **目录结构**：列出关键目录层级（可用代码块画树状图）
- **文件类型分布**：N 个 SKILL.md / M 个 agent / K 个 command / J 个 hook（实际数）
- **编排关系**：谁调用谁？是平列还是分层？有没有 router / meta skill？
- **跨件契约**：文件之间如何引用、依赖、传递上下文？

### 1.3 设计思路 / 方法论
- **核心设计哲学**：（如「协议化 frontmatter」「约定优于配置」「单职责 skill」）
- **解决什么问题**：作者心里要解决的原始问题是什么？
- **做了什么 trade-off**：控制粒度 vs 上手难度 / 独立仓库 vs monorepo / 集中 vs 分散
- **反映什么认知模型**：作者如何看待 AI agent / skill / NL programming？

---

## 二、架构作为可学习模式（横向）

### 2.1 模式归类
给这个仓库的架构起一个**模式名**（例：「NL 表皮 + 原生二进制核心」「Router + Channels 分层」「单仓多 skill 平铺」），并解释这个模式的关键特征是什么。

模式特征清单（3-5 条）：
- 特征 1：…
- 特征 2：…

### 2.2 适用场景
这个架构最适合什么样的项目？什么时候**不要**用？

| 场景 | 适不适用 | 原因 |
|---|---|---|
| 例：需要系统级权限的桌面工具 | ✅ 高度适用 | 性能 + 跨平台优势明显 |
| 例：纯数据处理脚本 | ❌ 不适用 | 用脚本就够，二进制是过度工程 |

### 2.3 与其他架构对比
列出 2-3 个备选架构，用表格对比 trade-off：

| 架构 | 典型代表 | 优势 | 劣势 |
|---|---|---|---|
| 本仓库的架构 | … | … | … |
| 备选 A：… | … | … | … |
| 备选 B：… | … | … | … |

### 2.4 改进空间
如果是我自己设计这个项目，会怎么改？2-3 个**具体可执行**的改进点，不要"应该更好"这种空话。
1. **当前问题**：… **改进做法**：… **预期收益**：…

## 三、过去审查发现（YYYY-MM-DD 历史快照）

### 3.1 当时质量评分（NLPM）
该仓库 YYYY-MM-DD 当时得分 N/100。

| 文件 | 当时分数 | 主要问题 |
|---|---|---|

### 3.2 当时值得借鉴的模式
3-5 个。每条：**模式名** → 为什么好（根本原因）→ 原文示例路径 → 如何借鉴

### 3.3 当时的缺陷
至少 3 条。每条：**问题** → 为什么这么设计会失败（根本原因，不只描述现象）→ 自查：我有没有犯同样的错？

### 3.4 当时的优化机会
前 3 条。注意仅用作学习材料，不用于 PR。

---

## 四、现在 vs 过去对比

### 4.1 关键缺陷在现仓库中的状态
拽 2-3 个代表性当时缺陷，查验现在状态：

| 过去缺陷 | 检查方法（grep / file read） | 现状 | 含义 |
|---|---|---|---|

### 4.2 架构演进
从当时 audit 的文件清单 → 现在的目录结构，有没有重组？新增了什么？删了什么？这说明作者后来意识到了什么？

### 4.3 新增的可学习模式
当前 HEAD 中出现、但过去 audit 未覆盖的设计是什么？如果没变化就写「暂无」。

## 五、校准

### 5.1 我已经在做对的
该仓库的哪些优秀模式我已经在应用？3-5 条。这是正向锚点，避免只从错误中学习。

### 5.2 挑战 / 验证
- **这次案例挑战了我什么假设？** 或
- **哪个我之前犹豫的做法被这次验证为对的？**
- 没冲突就写「本案例未产生认知冲突」

## 六、行动

### 6.1 自查动作
给出可直接跑的检查命令，不要抽象描述。例：

```bash
# 检查我的 skill 是否有模糊量词
grep -rn -E '\b(appropriate|comprehensive|robust|efficient)\b' ~/.claude/skills/*/SKILL.md
```

每条命令附一句「命中后怎么办」。

### 6.2 灵感 → 实施路径
2-4 个。每个：
- **想法**：…
- **为何可行**：…
- **第一步**：具体怎么开始（哪个文件、哪个 script、多长时间）

没灵感就写「暂无」。

## 七、对照我的 GitHub 仓库

> 数据源：`learning/my-repos.json`（由 `.github/workflows/refresh-my-repos.yml` 每周一 01:00 UTC 自动刷新，含 60 天内有 push 且有 NL 工件的公开仓库）

### 8.1 目的对齐度（这个仓库跟我的哪个项目最相似？）

- **本案例 OWNER/REPO 的核心目的**：[一句话提炼]
- **我的对应项目**：

| 我的仓库 | 相似度 | 相同点 | 不同点 | 借鉴优先级 |
|---|---|---|---|---|
| MarkQWu/drama-workshop-skills | 高/中/低/无 | … | … | 高/中/低 |

若全部「无」，写「我的仓库中无目的相近的项目，本节仅做技术模式对照」

### 8.2 在我的项目里复现的同类问题

对 §3.3「当时的缺陷」和 §4.1「现在仍存在的缺陷」逐条核查我的项目（用 my-repos.json 中 priority=high 的仓库做 grep 验证）：

| 本案例缺陷 | 检查方法（grep / file） | 我的项目命中情况 | 严重度 |
|---|---|---|---|
| 例：所有 SKILL 缺 `## Examples` | `grep -L '## Examples' my-repos/*/skills/*/SKILL.md` | drama-workshop-skills 命中 8/12 | 高 |

**命中后的具体行动建议**（不是抽象建议）：
- 仓库 X 的 文件 Y → 具体修法 → 5-30 分钟可完成

### 8.3 别人的更优方案（值得借鉴的）

本案例中比我的项目做得更好的具体做法：

1. **领域**：（如「frontmatter 协议化」）
   - **本案例做法**：（具体描述，给原文件路径）
   - **我的项目现状**：（哪个仓库哪个文件里更弱）
   - **如何借鉴**：（落地步骤、给出 git diff 思路或要改的文件）

### 8.4 反向：我的项目做得比他们好的地方

不只是单向学习。识别我的项目某个做法更优：
- **领域**：…
- **我的做法**：（哪个仓库哪个文件）
- **本案例做法**（弱在哪）：…
- **意义**：未来若被人审到，这是亮点；若考虑给上游 PR，这是切入点

若无写「本案例未发现我的项目更优的维度」。

## 八、术语表

这一节是给「不熟悉技术名词的读者」准备的。正文中第一次出现专有名词时用 `[xxx](#xxx)` 锚点链接到这里。

格式：

### <a name="xxx"></a>原生二进制核心
> 用 C / Go / Rust 这种"编译型语言"写出来、最终变成可执行文件（如 macOS 上的 `.app`、Linux 上的命令行程序）的程序。"原生"意思是不依赖额外的解释器（如 Python、Node.js）就能直接运行，"二进制"意思是文件内容是机器码不是文本。
> **对比**：脚本（如 bash、Python）= 文本，需要解释器；原生二进制 = 机器码，直接运行。性能高一个数量级。

### <a name="frontmatter"></a>frontmatter
> Markdown 文件最顶部用 `---` 包起来的一段 YAML 配置，用来声明文件的元数据（如 `name`、`description`、`model` 等）。Claude Code 读 SKILL.md 时先解析 frontmatter 才能知道这个 skill 怎么注册和调用。

### <a name="manifest"></a>manifest
> 项目的"清单文件"，告诉系统这个项目包含哪些组件。`plugin.json` 就是 Claude Code 插件的 manifest——里面列出所有 commands、skills、agents 的路径。如果 manifest 里漏写了某个文件，那个文件即使在硬盘上也不会被加载。

### <a name="OIDC-token"></a>OIDC token
> 一种短期身份证。GitHub Actions 在运行 workflow 时可以用 OIDC token 向 Anthropic 等服务证明"我是一个合法的 GitHub Actions 任务"，避免直接把长期 API key 放在仓库里。

## 数据源约定

- **过去维度**（第三章 + 第四章「过去缺陷」列）：仅从 `auditor/audits/<slug>.md` + `.findings.jsonl` 取
- **现在维度**（第一章 + 第二章 + 第四章其他）：用 `git clone --depth 1` 实时拉公开仓库（避开 GitHub API 限速）
- **跨引用**：`case-studies/<date>-<slug>.md` 如存在（xiaolai 案例），可读取后在 1.2/1.3/2.x 引用

## 主题标签约定

常用标签集合（用英文小写，便于检索）：
- `cross-reference` — 跨件互引、router、meta skill
- `template-design` — 模板复用、frontmatter 约定
- `vague-quantifier` — 模糊量词、可验证标准
- `security-gate` — 安全约束、权限收敛、白名单
- `model-pinning` — 模型版本固定
- `examples-driven` — 示例驱动、input→output 模式
- `manifest-discipline` — manifest 同步、契约守护
- `single-purpose` — 单职责 skill / agent
- `experience-accumulation` — 经验侧车文件、跨会话学习
- `fallback-chain` — 降级路径、错误处理协议
- `nl-binary-hybrid` — NL 表皮 + 原生二进制（如 claude-notifications-go 类型）
- `router-channels` — 路由层 + 渠道层分层架构
- `monorepo-vs-split` — 单仓多 skill vs 拆分仓库的设计选择
- `offline-capable` — 离线部署、不依赖网络的设计
- `curl-pipe-bash-risk` — curl|bash 远程执行的安全反模式

发现新模式时可加新标签，但同义词尽量复用上面的。
